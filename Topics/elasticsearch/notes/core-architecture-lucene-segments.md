# コアアーキテクチャとLuceneセグメント

## 全体構造

```
Cluster
  └─ Node (複数)
       └─ Index (論理単位)
            └─ Shard (物理Luceneインデックス)
                 └─ Segment (不変ファイル群)
```

## Luceneセグメントとそのライフサイクル

各シャードは内部的にApache Luceneのインデックスであり、**セグメント**と呼ばれる不変ファイルの集合で構成される。

### 書き込みフロー

```
ドキュメント書き込み
  → Translog（WAL）に記録（ノード障害時の復元用）
  → In-memoryバッファに蓄積
  → Refresh（デフォルト1秒ごと）
      → 新しいセグメントとしてディスクへフラッシュ
      → この時点で検索可能になる（near-real-time）
  → Flush（Translogが一定サイズ≈512MBに達したとき）
      → 全セグメントをコミット → Translogをクリア
  → Merge（バックグラウンドで自動実行）
      → 小さなセグメントを大きなセグメントに統合
      → 削除済みドキュメントを物理削除
```

### セグメントの不変性

セグメントは**書き換え不可**（immutable）。更新はいったん「削除フラグ」をつけ新セグメントに新版を書き込む。Mergeのタイミングで削除フラグが付いたドキュメントが物理削除される。

## シャードとレプリカ

- **Primary Shard**: 各ドキュメントは1つのプライマリに属する。インデックス作成時に数を固定（後から変更不可）。
- **Replica Shard**: プライマリの読み取り専用コピー。数はいつでも変更可能。障害時のフェイルオーバーと読み取りスケールアウトの両方に使う。

### シャード数の目安

- 最適シャードサイズ: **10〜50GB**
- 1シャードあたり最大文書数: **2億件以下**
- シャード数の変更: 再インデックスが必要（Shrink/Split API、またはReindex API）

## ノードロール

| ロール | 役割 |
|---|---|
| **master-eligible** | クラスタ状態管理・シャード割り当て決定。専用ノードを推奨（データ処理をしない） |
| **data** | シャードの保持・インデックス/クエリ処理 |
| **ingest** | ドキュメント取り込み前の変換処理（パイプライン実行） |
| **coordinating only** | リクエスト受信→各データノードへのルーティング→結果集約。専用化でスケール改善 |
| **ml** | 機械学習モデル推論専用 |

小規模クラスタでは全ロールを1ノードが兼務。大規模環境ではロール分離が推奨。

## マスター選出とクラスタ状態

Raftベースの合意アルゴリズム（Elasticsearch 7.0以降）でマスターを選出。クラスタ状態（インデックス設定・シャード配置）はマスターが管理し全ノードに配信する。

**スプリットブレイン対策**: 奇数台のmaster-eligibleノードを配置し、quorum（過半数）を維持する。
